# docs 里的图片是怎么来的

README 和说明文档里的宣传图不是手工截的位图，而是**可复现的渲染结果**：改文案、改截图后重跑渲染即可，
不需要设计工具，也不会出现"图里的字和文档对不上"。

---

## 一、可复现的渲染源

| 产物 | 渲染源 | 视口 | 内容 |
|---|---|---|---|
| `hero.png` | `hero.html` | 1200×420 | README 首图：品牌、三步流程、主界面截图 |
| `social-preview.png` | `social-preview.html` | 1280×640 | GitHub 社交预览卡（分享链接时显示的图） |

渲染方式：用 Chrome 无头模式打开对应 `.html`，按上表视口截图，把 PNG 覆盖到本目录。

**为什么不再用手工位图**：旧的 `hero.png` 是控制台 TUI 的截图——实测 **94% 的像素是深色**
（黑底控制台的特征），而程序早已是图形界面。首图放着一张过时的界面，是宣传页最容易漏掉、
也最影响第一印象的错误。改成 HTML 渲染后，界面换了只要重跑一次。

`hero.html` 里引用的界面截图是 `main-window.png`，取自真实的程序窗口。

---

## 二、界面截图（直接从程序截取）

| 文件 | 内容 | 被谁引用 |
|---|---|---|
| `main-window.png` | 主窗口：三个分区 + 按钮行 | `README.md`、`README.zh-CN.md`、`GUI.md` |
| `versions.png` | 版本选择对话框 | `GUI.md` |
| `browser.png` | 数据目录对话框 | `GUI.md` |

截图方法：启动程序对应模式（`check` / `picker` / `browser` / `click`），把窗口置顶后抓取，
**不合成、不修饰**——文档里的图必须和用户看到的一致。
